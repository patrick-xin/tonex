# User guidance is three non-overlapping surfaces, classified by the nature of the help — not the control it explains

The clarity findings that prompted this work all share a shape: a control does something non-obvious (the chroma ceiling moves, a CMF second source has no visible effect under some presets, a custom color expands to a different token set per layer), and the editor said nothing about it. The reflexive fix is per-control help — a "?" button or persistent tooltip next to each axis. Taken to its conclusion that buries the rail under question marks, scatters the same explanation across every place a concept appears, and still leaves a first-time user with no sense of the whole. The editor is a dense rail of interacting controls; "explain everything in place" and "keep the rail legible" are in direct tension, and per-control help resolves it the wrong way.

**Decision:** all user guidance is partitioned into exactly three surfaces, each owning one job, and a given piece of guidance is assigned to a surface by **what kind of help it is**, not by which control it concerns:

- **Orientation (the tour)** — a first-run, sequential walkthrough that tells a new user what the major moves are and roughly where they live. One tight sentence per stop; it never carries reference depth — it defers that to the reference surface via a "Learn more" link.
- **Reference (the help dialog)** — the on-demand, canonical home for every "what is this / why does it behave this way / how do I…" answer. It is the single source of truth for explanatory prose, opened deliberately, and read top-to-bottom or jumped into by deep-link.
- **Inline cues** — short, **state-triggered** microcopy that appears only when the live state makes it relevant (a slider is disabled, a level is at its floor, a choice has no effect under the current preset) and disappears otherwise.

The partition is a rule, not a tendency: persistent reference prose never lives inline or on the rail, canonical depth never lives in the tour, and a cue that isn't conditioned on live state isn't an inline cue. There are **no per-control "?" buttons and no persistent per-axis tooltips** — that is the specific failure mode this decision exists to forbid.

**Why three surfaces and not one:** the three differ by *trigger and lifetime*, which is exactly what makes them non-substitutable. Orientation is needed once, unprompted, and must be skimmable; reference is needed repeatedly, on demand, and must be complete; an inline cue is needed only in a transient state and must be invisible the rest of the time. A single surface tuned for any one of these is wrong for the other two — a tour long enough to be a reference is too long to onboard, a reference terse enough to onboard is useless as a reference, and a cue that's always visible is clutter.

**Why the non-overlap rule is load-bearing, not tidiness:** the same concept legitimately surfaces in more than one place (the tour mentions export, the reference explains it; an inline cue names a condition the reference also documents). If each surface held its *own* full copy of the explanation, they would drift independently and the product would contradict itself. The rule resolves this: depth has exactly one home (reference), and the other surfaces *point at it* rather than restate it. Orientation and inline cues may paraphrase a concept in shorter form on purpose — that is the model working, not drift — but only the reference surface owns the authoritative wording. This is also why guidance that feels like reference must route into the dialog even when it's "about" a specific rail control: putting it on the rail would both clutter the rail and fork the canonical copy.

**Why the tour is layer-scoped but the reference shows both layers:** a user works in one layer at a time (ADR-0013), so orientation tours *their* workspace — showing shadcn-only stops to an md user is noise about a place they aren't. Reference is the opposite: a cross-layer "how does md differ from shadcn here?" is a first-class question, so the dialog answers for both layers regardless of where it's opened. Trigger again decides surface: orientation is contextual to the current workspace, reference is comprehensive across workspaces.

**Why the tour is desktop-only, and what a mobile tour would actually be:** the tour orients by spotlighting real controls in place, which presumes those controls are laid out as the desktop rail presents them. Below the rail breakpoint the rail collapses into a drawer and those targets aren't simultaneously on screen, so a spotlight has nothing stable to point at. We did **not** respond by shrinking the desktop tour to fit — on mobile the system instead routes a new user to the reference surface, which needs no on-screen anchors and already carries the same explanations. The consequence to record for a future session: **a mobile tour is not the desktop tour reflowed; it is a separate orientation of a separate layout.** The mobile editor surfaces the same *concepts* through a different arrangement (drawers, sheets, a different disclosure order), so a mobile tour would need its own stop list anchored to mobile's controls and its own sequencing — while still obeying this ADR (orientation only, one sentence per stop, depth deferred to the shared reference). The reference dialog is the layout-independent surface and is the right place for any guidance that must reach every viewport; the tour is the layout-dependent one and is correctly gated to the layout it was built for. A second consequence: the assumption that only one tour instance is ever live at a time is what keeps the orientation surface simple, and that assumption holds *because* the tour is desktop-only — a mobile tour is a second live context and must not silently inherit the single-instance shortcut.

**Consequence:**

- Adding guidance starts with a classification, not a component: is this orientation (→ a tour stop, one sentence, link out), reference (→ a dialog section, canonical depth), or a reaction to live state (→ an inline cue, conditioned on a predicate)? "I'll add a tooltip to this control" is not an available answer. This is the question a future session asks before extending the system, and answering it keeps additions consistent without re-deriving the model.
- Because depth has one home, the surfaces that point at it must stay reachable: an orientation "Learn more" must resolve to a real reference section. That cross-surface link is the one coupling worth mechanically guarding; everything else is intentionally-paraphrased restatement and is left to prose.
- Copy that two surfaces must show *verbatim* (a label the user reads in the UI and again in the reference) is the only case for a shared constant; copy that each surface phrases for its own job is deliberately not shared, because forcing it to match would defeat the per-surface tuning the three-surface split exists to enable.
- The reference surface is the safe default when a viewport, layout, or future surface can't host the others: it is on-demand, anchorless, and layer-complete. Orientation and inline cues are enhancements layered on top of it, not prerequisites for the product being explainable.

## Where it lives

The three surfaces' homes and the steps to extend each are imperative reference, not rationale — they live in [`rules/guidance.md`](../agents/rules/guidance.md). This ADR keeps only the *why*. The one coupling worth guarding mechanically — a tour `learnMore` must resolve to a real reference section — is asserted by `help-sections.test.ts`, so a dangling deep-link fails the suite rather than shipping.
